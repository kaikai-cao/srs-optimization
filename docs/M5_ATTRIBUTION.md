# M5 归因报告（M5-D / M5-E）

本文件回答一个问题：**p16 / p18 的 `prepared_verify` 峰值工作集，有多少能被逐 Worker 的分配史解释。**
所有数字来自探针（M5-B）在 `results/raw/m5d/` 下的 12 次运行：每档 3 次 `pristine` + 3 次 `trace` 交错，
每次 trace 都过 L1（调用序列）与 L2（逐 Worker 无容差回放）。汇总文件在 `results/processed/m5d_attribution_p1{6,8}_r{1,2,3}.*`。

> 上一轮（M5-A）用同一套源码推出的静态账本，现在被逐项检验。结论是：
> **两个"状态量"精确命中，"同时在场"这个假设不成立**——这是本文件最重要的一句话。

---

## 0. 结论摘要

1. **在途峰值精确命中，且峰值构成单一**：p18 实测 in-flight 峰 **987.4 MiB**，静态账本 **987.4 MiB**；
   峰值时刻 100% 来自 `tauG1_19_transformed`（`resLagrange @ 2^19` 的 28 个在途任务）。p16 是 **265.1 / 265.1**。
   这不是"接近"，是同一个数。
2. **容量池终值精确命中，且逐 Worker 分布一致**：p18 实测终值 **25,288 页 = 1,580.5 MiB**，模型 **25,288 页**；
   逐 Worker 为 **20 × 1044 + 8 × 551**，与模型预测的分布逐项相等。p16 实测 **6,826 页 = 426.6 MiB**，
   逐 Worker **22 × 276 + 2 × 153 + 4 × 112**，同样逐项相等。L2 在 20,145 / 16,582 个任务上零容差通过。
3. **但"在途"与"容量"不同时到顶**：p18 在途峰值发生在 `t = 30.7 s`，那一刻容量池只有 **778.3 MiB**
   （终值 1,580.5）；容量池到终值时在途已经回落到 0。**把两者相加当"峰值预测"在时间上是错的**，
   这与 §5.6 早就写下的"不得跨量纲相加"是同一件事，现在有了实测支撑。
4. **残差是区间的，而且区间很宽**：p18 在途峰值时刻 WS = 3,260–3,368 MiB。若容量按**当时已达到的** 778.3 MiB 计入，
   残差 **1,494–1,603 MiB**；若容量按**终值** 1,580.5 计入（即假设扩容早已可见），残差 **692–791 MiB**。
   区间下端与上端的差别全部来自"扩容何时可见"，**不是**来自 WS 采样。
5. **残差本身在三次运行之间就不稳定，所以它不能被归给某个固定机制**：p18 结束时在途 = 0、容量 = 1,580.5，
   残差三次分别是 **853–875 / 1,397–1,452 / 1,099–1,133 MiB**，极差约 **600 MiB**；
   而同一批运行的探针量（在途、容量、grow 次数）三次**完全相同**。
   结论只能写成下界：**p18 至少有 0.85 GiB 的驻留既不来自在途也不来自 Worker WASM 容量**；
   p16 的同口径下界是 **0.79 GiB**（三次 790 / 861–884 / 826–827）。**不可以说它是"某个机制的 X MiB"。**
6. **H1（FFT 输入副本）被排除为主因**：p18 的 FFT 在途从未超过 16 MiB（32 分片 × 16,384 点 × 32 B），
   在 987 MiB 的在途峰里占比 < 2%；即便全算进去也只能解释结束残差的 2%。它不能解释第 5 条的 0.85 GiB。

## 1. 数据与门槛

| 项 | p16 | p18 |
| --- | ---: | ---: |
| fixture | `pot16_final.ptau` | `pot18_final.ptau` |
| 运行次数 | 3 pristine + 3 trace（交错 a/b） | 同左 |
| 探针事件 | 50,178 / 次 | 60,960 / 次 |
| 任务数 / 调用数 | 16,582 / 360 | 20,145 / 445 |
| `memory.grow` 事件 | 110 | 180 |
| `alloc_base` | 102,328 B（全部任务一致） | 102,328 B |
| L1 | PASS（360/360） | PASS（445/445） |
| L2 | PASS（0 fails，`maxpages` 逐 Worker 相等） | PASS（0 fails） |
| trace 与 pristine 的 peak WS | 1,474–1,591 vs 1,503–1,551（区间重叠） | 3,691–3,763 vs 3,724–3,781（区间重叠） |

**探针扰动**：p16/p18 上 trace 与 pristine 的 peak WS 区间重叠、耗时差在噪声内
（p18：trace 57.2–65.5 s，pristine 58.2–62.8 s）。p10 上测到的 +9% 写盘成本在这里被 60 s 的运行时摊薄。
**因此本文件的归因不依赖"探针无扰动"这个假设，而依赖探针事件的完备性（L1/L2 可验证）。**

## 2. 两项精确相等的量

### 2.1 在途峰值（JS 字节，主线程 → Worker 的结构化克隆）

| power | 静态账本 | 实测 | 峰值时刻构成 |
| ---: | ---: | ---: | --- |
| 16 | 265.1 MiB | **265.1 MiB** | `tauG1_17_transformed`（28 个在途任务） |
| 18 | 987.4 MiB | **987.4 MiB** | `tauG1_19_transformed`（19 个大分片 + 9 个尾部分片） |

实测值由 `task_send` 的 `t_ms` 与 `task_done` 的 `t_ms` 做区间扫描得到（`scripts/m5d_attribution.cjs`），
**不依赖任何采样**，所以它与模型之间的相等不是"落在误差内"，而是同一个整数。

### 2.2 容量池终值（WASM 地址空间）

| power | 静态账本 | 实测 | 逐 Worker 分布（实测 = 模型） |
| ---: | ---: | ---: | --- |
| 16 | 6,826 页 = 426.6 MiB | **6,826 页 = 426.6 MiB** | 22 × 276 + 2 × 153 + 4 × 112 |
| 18 | 25,288 页 = 1,580.5 MiB | **25,288 页 = 1,580.5 MiB** | 20 × 1044 + 8 × 551 |

L2 把这 180 / 110 个 `memory.grow` 事件逐条回放，`from_pages → to_pages`、`wasm_after`、`alloc_top`
逐 Worker 相等。也就是说：**`alloc()` 的双计（F4）、Worker 容量单调不缩容（F7）、
首轮任务落 `workers 0..C-1`（§5.0.1 的推论）这三条，第一次被完整验证。**

## 3. 同刻并列（L3）：四个量放在一个时钟上

残差 = WS − 在途 − 容量。WS 由测量器每 25 ms 采样，探针事件是精确时间戳，所以残差给的是**区间**。

### p18（三次 trace，逐次列出，不舍并）

| run | t 峰值 (ms) | 在途 | 容量(当时) | WS @峰值 | 残差 @峰值 | WS @结束 | 残差 @结束 |
| --- | ---: | ---: | ---: | --- | ---: | --- | ---: |
| r1 | 30,668 | 987.4 | 778.3 | 3,358.7→3,368.4 | **1,593–1,603** | 2,455.2→2,433.4 | **853–875** |
| r2 | 28,511 | 987.4 | 778.3 | 3,260.1→3,304.2 | **1,494–1,538** | 3,032.6→2,977.4 | **1,397–1,452** |
| r3 | 28,461 | 987.4 | 778.3 | 3,336.7→3,324.5 | **1,559–1,571** | 2,714.0→2,679.4 | **1,099–1,133** |

### p16（同口径）

| run | t 峰值 (ms) | 在途 | 容量(当时) | WS @峰值 | 残差 @峰值 | WS @结束 | 残差 @结束 |
| --- | ---: | ---: | ---: | --- | ---: | --- | ---: |
| r1 | 9,007 | 265.1 | 215.0 | 1,317.0→1,313.2 | **833–837** | 1,216.8→1,216.8 | **790** |
| r2 | 8,901 | 265.1 | 215.0 | 1,297.1→1,272.6 | **792–817** | 1,310.3→1,288.0 | **861–884** |
| r3 | 8,834 | 265.1 | 215.0 | 1,318.1→1,335.7 | **838–856** | 1,252.8→1,253.4 | **826–827** |

> 三次运行的**探针量完全相同**（在途 987.4 / 265.1，容量 778.3 / 215.0，终值 1,580.5 / 426.6），
> 而 **WS 与残差每次都不一样**。这是本文件最该被记住的事实：残差的波动来自被测进程，不来自探针。

### 起点基线（首个 `task_send` 之前，在同刻表里逐次给出）

| power | 基线 WS | 用途 |
| --- | ---: | --- |
| 18 | 439.9 / 439.9 / 443.3 MiB | 减掉它之后，结束残差里"在这段窗口内新产生且未释放"的部分 ≈ 410–1,010 MiB |
| 16 | 443.9 / 437.9 / 444.6 MiB | 同上，≈ 346–440 MiB |

### 怎么读这张表

1. **不能写成"模型预测 2,568 MiB，实测 3,360 MiB，误差 30%"**：2,568 是"在途峰 + 容量终值"，
   这两个量从未同时成立。§5.6 的分子（段增量 2,396.5 MiB）走的是另一条口径（段内容量增量 + 在途），
   与实测段增量 2,160–2,636 对齐（0.99×），那是**窗口量**，不是瞬时量。
2. **同一时刻能确定的只有三项**：在途（精确）、容量（精确、但"何时可见"只能定位到任务结束）、
   WS（25 ms 粒度）。残差就是这三者的差，**本文件不把它归给任何机制**。
3. **在途回落到 0 之后的残差才是"非任务内存"的下界**：p18 **≥ 853 MiB**、p16 **≥ 790 MiB**（三次中的最小值）；
   减掉首个任务之前的基线（440 / 444）后，**至少 410 / 346 MiB** 是在这段窗口里产生且没有释放的。
   上端不能引用：p18 第三次的结束残差到了 1,452 MiB，说明这一项大部分是进程级可变开销，不是稳定结构。

## 5. 四个假设的判定

| 假设 | 判定 | 证据 |
| --- | --- | --- |
| **H-A**：p18 tauG1 段增长主要来自 `resLagrange` 的克隆在途 | **成立（成分被坐实）** | 在途峰 987.4 MiB 且 100% 为 `tauG1_19_transformed`；无其它 site 贡献 |
| **H-B**：Worker 容量 ≈ 2× 首个大分片（`alloc()` 双计），结束后不回落 | **成立（精确）** | 25,288 页与模型逐 Worker 相等；180 个 grow 事件零容差回放；L2 无一处回落 |
| **H-C**：p18 `prepared_verify` 中 FFT + FastFile 合计 < 160 MiB | **成立** | FFT 在途 ≤ 16 MiB；FastFile 页池 52.8 MiB（M4.1 已测），两者相加 < 70 MiB |
| **H-D**：`prepare_phase2` 的峰值主体无法由任何单次分配解释 | **未在本题上检验**，但 p18 结束时 ≥ 0.85 GiB 的残差给出了同类现象的下界 | 见 §3 第 3 条；`prepare_phase2` 需要单独一轮 |

## 6. 仍未解释的部分，以及下一轮怎么问

- **在途峰时刻的 692–1,603 MiB**：上下端的差（≈ 900 MiB）就是"容量何时可见"的不确定度。
  要收紧它，需要把 `memory.grow` 的时间戳从"任务结束时"改到"grow 发生的 alloc 内"——
  即让 `grow_events` 带自己的 `t_ms`（当前版本只在 `worker_task` 里给出最终状态）。
- **结束残差 790–1,452 MiB**：其中约 440 MiB 是任务开始前的进程基线（node + snarkjs + 读 fixture），
  另外 346 MiB 起（p16 最小值）到 1,010 MiB（p18 最大值）在这段窗口内产生。三次之间差 600 MiB，
  说明它有相当一部分是进程级可变开销，**必须先把它拆开才谈优化**。候选：主线程 `BigBuffer` 分片（`batchToMontgomery` 的
  16 MiB 级副本）、FastFile 页池（52.8 MiB）、V8 未回收的 `ArrayBuffer`、以及 WS 与 `arrayBuffers` 的统计差。
  **本轮不判定是哪一个**；`measure_m5.ps1` 已留 `-HeapSampleMs` 钩子，下一轮用 `heap_sample.array_buffers`
  与 `fft_assembly` / `batchconvert_copy` 事件去分。
- **不做的事**：不写优化代码、不改依赖、不动 `m1-m2-frozen`、不跑 p20/p21。
  在残差被拆开之前，任何"省内存"的改动都无法证明收益来自它自己。
